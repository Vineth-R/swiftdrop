What you can build

  • Create a delivery order when your store packs an item.
  • List and filter the orders you created.
  • Read one order with its fee snapshot and status timeline.
  • Download a branded PDF receipt for an order.
  • Receive signed status webhooks and update your own system.

1. Overview

SwiftDrop is a parcel delivery platform. The merchant API lets an approved merchant create delivery orders server-to-server and follow their progress. SwiftDrop calculates the delivery fee and returns an SDN tracking number. The merchant remains the owner of the customer relationship; SwiftDrop owns the parcel and delivery workflow.

Base URL

All routes in this guide are relative to the gateway base URL: https://<your-swiftdrop-host>/api/v1. The local development gateway is http://localhost:8080/api/v1.

Content type

Send Content-Type: application/json for every request with a body. Send Accept: application/json; the receipt endpoint returns application/pdf.

Rate limit

Order creation is limited to 120 requests per minute per API key. A limit breach returns 429 RATE_LIMITED. List, detail and receipt reads are not subject to that creation limiter, but normal gateway limits still apply; cache reference data such as zones rather than fetching it for every order.

Idempotency

Two independent idempotency mechanisms protect order creation:

  • externalOrderId is your own order reference. Reusing it with the same normalized payload returns the original order with 200 instead of creating a second parcel.
  • The optional Idempotency-Key header (up to 100 characters) identifies one attempt. Reusing it with the same payload also returns the original order.

If the same reference or key is reused with a different payload, the API returns 409 DUPLICATE_ORDER. Generate a new key for each new attempt and persist it with the request you sent.

Never lose an order to a timeout. Retry the same request with the same Idempotency-Key and payload. A lost response is safe to retry; a new payload under the same key is not.

2. Authentication boundaries

SwiftDrop has two different credential types. Use the right one for the right surface.

Surface Credential Where it is used
Merchant portal MERCHANT session (HttpOnly cookie) Dashboard, business profile, API-key management, webhook settings, order screens, receipt downloads
Server-to-server order integration X-API-Key Create, list, detail and receipt endpoints. The key stays on your server and is never sent to a browser.
Order reads and receipt Either a MERCHANT session or X-API-Key The order read/receipt routes accept both; the create route is API-key only.

API keys

  • Create and revoke keys in the merchant portal under API keys.
  • The full key is shown once, at creation. SwiftDrop stores only a hash.
  • Send it as X-API-Key: sdk_live_.... A missing, unknown or revoked key returns 401 INVALID_API_KEY.
  • An approved merchant is required. A pending, rejected or suspended merchant returns 403 MERCHANT_NOT_APPROVED.
  • Revoke a key immediately if it is exposed, then create a replacement.

Merchant identity is never in the request body

The merchant is resolved from the API key or session. Do not send a merchantId, ownerUserId or any identity field in an order request; unknown fields are rejected with 400 BAD_REQUEST. Another merchant's orders are not readable with your credential.

Pickup zone

If you omit pickup on an order, SwiftDrop uses the pickup address and zone configured on your merchant business profile. Include pickup only when this order ships from a different place.

4. Create an order

POST /api/v1/merchant/orders
X-API-Key: <your key>
Idempotency-Key: order-100245
Content-Type: application/json

Request fields

Field Type Required Rules
externalOrderId string yes 1–100 characters; your own reference
pickup contact no Omit to use the merchant profile pickup
recipient contact yes Name, phone, address, city and zoneId
weightKg number yes Greater than 0, at most 9999.99; up to 2 decimals
sizeCategory string yes SMALL, MEDIUM, LARGE or OVERSIZED
description string no At most 255 characters

Contact fields

Field Rules
name At most 150 characters
phone Use E.164, for example +94712345678
address At most 255 characters
city At most 100 characters
zoneId A UUID from GET /api/v1/zones

A missing order and another merchant's order both return 404 NOT_FOUND. Do not use a UUID's unguessability as an authorization control; SwiftDrop scopes every query to the authenticated merchant.

7. Download a receipt

GET /api/v1/merchant/orders/{trackingNumber}/receipt
X-API-Key: <your key>

Example with a real tracking number: GET /api/v1/merchant/orders/SDN4T8W2LC6/receipt.

Returns a private, branded PDF for the order with that tracking number. The route accepts a merchant session cookie or an API key. The tracking number is a lookup key, not an authorization token: the order must belong to the authenticated merchant, otherwise the response is 404 NOT_FOUND.

Response 200

Content-Type: application/pdf
Content-Disposition: attachment; filename="SwiftDrop-order-SDN4T8W2LC6.pdf"
Cache-Control: no-store

The PDF contains the SwiftDrop wordmark, receipt title, tracking number, external order reference, merchant and pickup details, recipient details, parcel description/weight/size, the fee breakdown, current status and the recorded status timeline. The fee is a snapshot, not a payment receipt.

Download from the portal

Open an order in the merchant portal and choose Download receipt. The browser downloads SwiftDrop-order-<trackingNumber>.pdf.

8. Status lifecycle

Merchant orders mirror the parcel status that SwiftDrop records. The allowed transitions are:

From Allowed next
CREATED PICKED_UP, FAILED
PICKED_UP IN_TRANSIT, FAILED
IN_TRANSIT OUT_FOR_DELIVERY, FAILED
OUT_FOR_DELIVERY DELIVERED, FAILED
DELIVERED Terminal
FAILED Terminal

Each accepted transition is written to the order timeline. A courier pickup includes proof of pickup; a delivery includes proof of delivery and a recipient. A failed delivery records a failure reason. The merchant order status is synchronized from the parcel status.

Notifications and webhooks are triggered by status changes. The exact public webhook event is parcel.status_changed; the internal RabbitMQ event is parcel.status_changed.v1.

9. Webhooks

Configure the webhook URL and signing secret in the merchant portal. SwiftDrop sends an HTTP POST whenever a parcel linked to your merchant changes status.

Headers

Header Meaning
Content-Type application/json
X-SwiftDrop-Event parcel.status_changed
X-SwiftDrop-Event-Id Stable event ID; use it to ignore duplicates
X-SwiftDrop-Timestamp Unix seconds when the request was signed
X-SwiftDrop-Signature sha256= plus the lowercase hex HMAC-SHA256 of <timestamp>.<raw body>

Body

{
  "eventId": "6c8f8e56-5c6b-4d7c-9d9a-5f0f1f2b3c4d",
  "eventType": "parcel.status_changed",
  "schemaVersion": 1,
  "occurredAt": "2026-11-20T13:00:00Z",
  "data": {
    "trackingNumber": "SDN4T8W2LC6",
    "externalOrderId": "SZ-100245",
    "previousStatus": "PICKED_UP",
    "status": "IN_TRANSIT",
    "note": null,
    "failureReason": null
  }
}

Verify the signature

Verify the HMAC against the raw request body, not a parsed and re-serialized object. Reject timestamps outside five minutes in either direction, and compare signatures in constant time. 

const crypto = require('crypto');

function verifySwiftDrop(secret, headers, rawBody) {
  const timestamp = headers['x-swiftdrop-timestamp'];
  const received = headers['x-swiftdrop-signature'];
  if (!timestamp || !received) return false;

  const now = Math.floor(Date.now() / 1000);
  const sent = Number(timestamp);
  if (!Number.isInteger(sent) || Math.abs(now - sent) > 300) return false;

  const expected =
    'sha256=' +
    crypto
      .createHmac('sha256', secret)
      .update(timestamp + '.')
      .update(rawBody)
      .digest('hex');

  const a = Buffer.from(expected);
  const b = Buffer.from(received);
  return a.length === b.length && crypto.timingSafeEqual(a, b);
}

Delivery rules

  • Respond with any 2xx within 10 seconds. Any other result counts as a failure.
  • Failed deliveries are retried after approximately 1 minute, 5 minutes, 30 minutes, 2 hours and 6 hours (six business attempts including the first).
  • After exhaustion the event is dead-lettered and no further automatic attempt is made.
  • A suspended, pending or rejected merchant, or an inactive/unsubscribed webhook, is suppressed before the request and is not retried on reinstatement.
  • Delivery is at least once. Deduplicate on the event ID (X-SwiftDrop-Event-Id / body eventId), not on the tracking number alone.
  • The webhook URL must be HTTPS, must resolve to a public address, and must not redirect.

10. Errors

Every error uses the same envelope:

{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "one or more fields are invalid",
    "details": [
      { "field": "recipient.zoneId", "issue": "must be a UUID" }
    ]
  },
  "meta": { "requestId": "req_error", "timestamp": "2026-11-20T13:00:00Z" }
}
Status Code What to do
400 BAD_REQUEST Malformed JSON or an unknown field. Send exactly the documented shape.
401 INVALID_API_KEY Missing, unknown or revoked key. Create a new key in the portal.
403 MERCHANT_NOT_APPROVED The merchant is pending, rejected or suspended.
404 NOT_FOUND The order does not exist, is another merchant's order, or the receipt tracking number is unknown.
409 DUPLICATE_ORDER Same reference or idempotency key with a different payload.
422 VALIDATION_ERROR Invalid fields. Read details[].field.
422 ROUTE_NOT_SERVICEABLE The pickup/destination zone pair is not priced.
422 WEIGHT_NOT_PRICED The weight is outside every active pricing band.
429 RATE_LIMITED More than 120 order creations per minute for one key. Back off.
503 SERVICE_UNAVAILABLE Parcel or Pricing is temporarily unavailable. Retry with the same key.

11. Quick start

Set these shell variables once:

export SWIFTDROP_HOST="http://localhost:8080"
export SWIFTDROP_API_KEY="sdk_live_..."
export DEST_ZONE="ff42248d-483c-4d0c-bc67-b97731c019c6"

1. Find a zone

curl -s "$SWIFTDROP_HOST/api/v1/zones"

2. Create an order

curl -s -X POST "$SWIFTDROP_HOST/api/v1/merchant/orders" \
  -H "X-API-Key: $SWIFTDROP_API_KEY" \
  -H "Idempotency-Key: SZ-100245" \
  -H "Content-Type: application/json" \
  -d '{
    "externalOrderId": "SZ-100245",
    "recipient": {
      "name": "Amali Fernando",
      "phone": "+94712345678",
      "address": "45 Lake Drive",
      "city": "Kandy",
      "zoneId": "'"$DEST_ZONE"'"
    },
    "weightKg": 1.5,
    "sizeCategory": "SMALL",
    "description": "Phone case"
  }'

3. List your orders

curl -s "$SWIFTDROP_HOST/api/v1/merchant/orders?page=1&pageSize=20" \
  -H "X-API-Key: $SWIFTDROP_API_KEY"

4. Read one order

curl -s "$SWIFTDROP_HOST/api/v1/merchant/orders/<orderId>" \
  -H "X-API-Key: $SWIFTDROP_API_KEY"

5. Download the receipt

curl -s -D receipt.headers \
  -o "receipt_SDN4T8W2LC6.pdf" \
  "$SWIFTDROP_HOST/api/v1/merchant/orders/SDN4T8W2LC6/receipt" \
  -H "X-API-Key: $SWIFTDROP_API_KEY"
Portal-only actions. API keys, webhook URL/secret settings, webhook test sends, delivery logs and the business profile are managed in the merchant portal with a MERCHANT session. They are not API-key endpoints and are not part of a server integration.

12. Support and versioning

This guide describes API v1.1 plus additive, backward-compatible merchant enhancements: the dedicated GET /merchant/orders/{trackingNumber}/receipt endpoint, the dedicated integration page and this guide. The existing orderId field and detail route remain unchanged.

  • The existing orderId field and GET /merchant/orders/{orderId} route remain supported.
  • New fields may be added in a backward-compatible way. Ignore unknown response fields.
  • Send only documented request fields; unknown request fields are rejected.
  • Keep your API keys, webhook signing secret and raw customer data out of logs and error reports.

Checklist before going live

  • Store the API key server-side and rotate it if exposed.
  • Fetch and cache the active zone list.
  • Persist orderId, trackingNumber and your externalOrderId.
  • Retry ambiguous failures with the same Idempotency-Key and payload.
  • Verify webhook signatures against the raw body and deduplicate on the event ID.
  • Respond to webhooks with 2xx within 10 seconds and move slow work to a queue.
