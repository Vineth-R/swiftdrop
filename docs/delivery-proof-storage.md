# Delivery proof storage

Delivery proof photographs are private objects. PostgreSQL stores only metadata
and the generated object key in `parcel.delivery_proofs.photo_path`; the bytes
never enter PostgreSQL and are never served from a public web path.

## Abstraction

`packages/go-common/objectstore` is infrastructure only. Parcel business logic
depends on the `Store` interface:

```go
Put(ctx, key, data, contentType) error
Delete(ctx, key) error
Exists(ctx, key) (bool, error)
Stat(ctx, key) (ObjectInfo, error)
List(ctx, prefix) ([]string, error)
PresignGet(ctx, key, ttl) (url string, expiresAt time.Time, error)
Open(ctx, key) (*Object, error)
Close() error
```

Adapters:

- `Local` — default development provider. Uses `os.Root`, creates a private
  `0700` directory and `0600` files, streams downloads through the API, and
  reports `ErrPresignUnsupported`.
- `S3` — AWS SDK for Go v2. Used by Neon Object Storage and local S3-compatible storage (VersityGW). Path-style
  addressing, static credentials, SigV4 presigned GET, `HeadObject`, and
  paginated `ListObjectsV2`.

Provider business logic never imports Neon-specific or AWS-specific types.

## Object keys

```text
<parcel-uuid>/<proof-uuid>.jpg
<parcel-uuid>/<proof-uuid>.png
```

- Generated by the server from the parcel UUID, proof UUID and verified MIME
  type. Client file names never reach storage.
- The legacy flat `<32 hex>.jpg|.png` keys remain readable and deletable so
  existing rows keep working until the transfer tool updates them.
- `photo_path` remains `VARCHAR(255)`; the new key is 77 characters.

## Configuration

```env
STORAGE_PROVIDER=local          # or neon, s3 (minio remains an alias)
STORAGE_LOCAL_DIR=              # local provider; falls back to PROOF_STORAGE_DIR
STORAGE_ENDPOINT=               # Neon branch storage endpoint or local S3 URL
STORAGE_REGION=us-east-2
STORAGE_BUCKET=delivery-proofs
STORAGE_ACCESS_KEY_ID=
STORAGE_SECRET_ACCESS_KEY=
STORAGE_USE_PATH_STYLE=true     # required by Neon and local S3-compatible storage
PROOF_MAX_SIZE_BYTES=5242880    # cannot exceed the database 5 MiB constraint
PROOF_PRESIGNED_URL_TTL_SECONDS=300
PROOF_MAX_PER_PARCEL=20
```

- Neon keys map directly to the credential's `token_id` and
  `s3_secret_access_key`.
- Never expose storage credentials to the browser or logs. Configuration errors
  never echo the secret.
- `STORAGE_PROVIDER` empty plus `PROOF_STORAGE_DIR` set selects local. No
  provider means proof routes stay registered and fail closed with `503`.

## Upload flow

`POST /api/v1/courier/deliveries/{parcelId}/proof`

1. Validate multipart shape, size, text limits and decoded JPEG/PNG content.
2. Verify the courier's current parcel assignment (no lock).
3. Check the per-parcel quota.
4. Generate the object key.
5. Upload the private object.
6. Begin a transaction, lock the parcel with `FOR UPDATE`, re-check assignment
   and quota, and insert the proof row.
7. Commit. If a definite database failure occurs, delete the uploaded object.
8. A transport error during `COMMIT` is resolved by probing the proof ID; if the
   row exists, the object is retained.

Database and storage are **not** one atomic transaction. The ordering and
compensation guarantee that a committed row references an object uploaded before
the commit, and that definite failures clean up the object. Cleanup failures are
joined into the error and never hide the original failure. Process crashes
between upload and insert can leave orphan objects; use reconciliation.

Unsupported content returns `415`, a photo above the configured limit `413`,
quota exhaustion `409`, and disabled storage `503`, matching API v1.1.

## Download flow

`GET /api/v1/parcels/{parcelId}/proof/photo`

- Roles: owning CUSTOMER, currently assigned COURIER, DISPATCHER, ADMIN.
- A foreign customer receives `404`; a foreign courier receives `403`.
- Returns the latest proof with a photo:
  ```json
  {
    "data": {
      "url": "https://…presigned…",
      "expiresAt": "2026-…Z",
      "mimeType": "image/jpeg",
      "stream": false
    },
    "meta": { "requestId": "…", "timestamp": "…" }
  }
  ```
- S3-compatible providers return a short-lived presigned GET URL (no permanent
  public URL).
- Local storage returns `stream: true` and the relative authorized content URL.
- `GET /api/v1/parcels/{parcelId}/proof/photo/content` streams the bytes through
  the service with the same authorization and `Cache-Control: no-store`.
- Missing metadata or a missing object returns `404 PROOF_PHOTO_NOT_FOUND`.

Existing API v1.1 courier/customer detail responses are unchanged; the new
routes are additive.

## Local S3-compatible storage

MinIO community images and binary downloads are no longer retrievable, so the
repository uses the pinned VersityGW S3-compatible gateway for local and CI
storage tests.

```sh
make storage-up
```

Starts VersityGW (Compose profile `storage`), waits for health, and creates the
`delivery-proofs` bucket. A separate `s3-meta` volume stores object metadata so
`Content-Type` survives `HeadObject`/presigned reads. Then set:

```env
STORAGE_PROVIDER=s3
STORAGE_ENDPOINT=http://s3:7070
STORAGE_ACCESS_KEY_ID=swiftdrop
STORAGE_SECRET_ACCESS_KEY=swiftdrop-s3
STORAGE_REGION=us-east-1
STORAGE_BUCKET=delivery-proofs
STORAGE_USE_PATH_STYLE=true
```

Host-side tools use `http://localhost:7070`. The default remains local
filesystem storage. No developer is forced onto Neon.

## Reconciliation and migration

`apps/services/parcel/proof-transfer`:

- Dry run: `make proof-transfer`
- Apply: `make proof-transfer-apply`
- Compare keys: `make proof-reconcile`

The report lists transferred, skipped, missing, failed and orphaned keys. It
never prints credentials, never deletes originals, and refuses to update a row
whose current key changed during the run.
