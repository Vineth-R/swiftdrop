## 7. Security Design

SwiftDrop protects accounts, parcel data and merchant integrations with layered controls. The gateway is the only public entry point. Every service checks the caller again, because the gateway and the browser are not trusted. This section lists each control, where it lives in the code and whether it is built yet. References such as API 2.2 and DB 3.4 point to the API Documentation v1.1 and the Database Design Document v1.1.

**Build status in this section** is written as of 1 November 2026. _Implemented_ means the code is merged and tested. _Partly implemented_ names what is still missing. _Planned_ names the task that builds it. The final report on 15 November replaces every _Planned_ with the real result.

### 7.1 Trust Boundaries

| Boundary                       | What crosses it                                           | Protection                                                                                                      |
| :----------------------------- | :-------------------------------------------------------- | :-------------------------------------------------------------------------------------------------------------- |
| Browser or API tool to gateway | Pages, JSON requests, cookies, WebSocket frames           | One origin, security headers, JSON-only bodies with size limits, cookies that scripts cannot read, rate limits. |
| Gateway to services            | Requests with `X-Request-Id` and `X-Real-IP`              | `/internal` is never routed. The services are not published on any host port.                                   |
| Service to service             | Quotes, courier eligibility, contacts, parcel summaries   | `X-Internal-Token` and `X-Request-Id` on every call, on the internal Docker network only.                       |
| Service to broker              | Status events                                             | Events carry identifiers and statuses, never addresses, phones, tokens or photos.                               |
| SwiftDrop to outside systems   | Google sign-in, email, merchant webhook URLs, AI provider | OAuth state and ID token checks, HTTPS-only and public-address-only webhook targets, signed webhooks.           |

### 7.3 Access Token and Session Credentials

The Identity service signs one access token per login and refresh. Every other service verifies it with the same shared package and the shared signing secret.

### Table 7.2: Access Token Claims

| Claim  | Meaning                                                          | Rule                                                                                                                                   |
| :----- | :--------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------- |
| `sub`  | The user's identifier (UUID).                                    | Required. Services use it for ownership checks and never trust a user ID sent by a client.                                             |
| `role` | One of `CUSTOMER`, `MERCHANT`, `COURIER`, `DISPATCHER`, `ADMIN`. | Required. A token with any other value is rejected.                                                                                    |
| `exp`  | Expiry time.                                                     | Required. Issue time plus 15 minutes.                                                                                                  |
| `iat`  | Issue time.                                                      | Required. A token issued in the future is rejected.                                                                                    |
| `jti`  | Unique token identifier.                                         | Required. 128 random bits. It identifies a token in audits and allows a future deny list.                                              |
| `iss`  | Issuer, fixed to `swiftdrop-identity`.                           | Written by the Identity service and required by every verifier. It is an implementation addition to the four claims listed in API 1.2. |

### Table 7.3: Credentials and Their Lifetimes

| Credential           | Form                            | Lifetime         | Where the browser keeps it                       | Where the server keeps it                                |
| :------------------- | :------------------------------ | :--------------- | :----------------------------------------------- | :------------------------------------------------------- |
| Access token         | Signed JWT                      | 15 minutes       | HttpOnly cookie `sd_access` (or a Bearer header) | Nowhere. It is verified by signature.                    |
| Refresh token        | Random `rt_` value              | 7 days, rotated  | HttpOnly cookie `sd_refresh` on `/api/v1/auth`   | SHA-256 hash, user agent and address in `refresh_tokens` |
| Password reset token | Random value in an emailed link | 30 minutes, once | Only in the link                                 | SHA-256 hash in `password_reset_tokens` (planned)        |
| OAuth state          | Random value                    | About 10 minutes | Only in the redirect URL                         | `oauth_states` (planned)                                 |
| Merchant API key     | `sdk_live_<lookup_id>_<secret>` | Until revoked    | The merchant's server, never a browser           | SHA-256 hash in `merchant_api_clients`                   |
| Webhook secret       | Random value                    | Until rotated    | The merchant's server                            | Encrypted in `merchant_webhooks` (planned)               |

### 7.5 Known Limits and Decisions

- **Access tokens cannot be revoked early.** They are verified by signature, so a token stays valid until it expires, at most 15 minutes after logout, a password change or a deactivation. Refresh tokens are revoked at once, so the session cannot be renewed. The short lifetime is the control.
- **One shared signing secret.** HS256 means every service that verifies a token holds the secret that could also sign one. This keeps the project simple. A public-key algorithm would let services only verify.
- **Role changes apply at the next refresh.** The role is inside the access token, so a changed role takes effect within 15 minutes.
- **Lockout can be abused.** Anyone who knows an email can lock that account for 15 minutes with five wrong passwords, and the `423` reply shows that the account exists. This is accepted because it also stops password guessing.
- **Rate limits are kept in memory per service instance.** That is enough for a single-instance deployment. Several instances would need a shared store.
- **Refresh token reuse is refused, not punished.** Reusing a rotated token fails, but it does not revoke the user's other sessions.
- **No email verification.** Registration does not confirm the email address (DB 3.2). Google sign-ups are marked verified.
- **Local development uses plain HTTP.** The Secure cookie flag and TLS belong to the deployment in front of the gateway.
