## Appendix: Threat List

This list names the main ways SwiftDrop could be attacked, the control that answers each one and the risk that remains. It covers login, Google sign-in, webhook signing and blocked private addresses, personal data, secrets and event replay. Section 7 holds the full controls. Status is as of 1 November 2026.

### Table A.1: Threats, Controls and Remaining Risk

| #   | Threat                                                                | Control                                                                                                                                                                                    | Remaining risk                                                               | Status                                          |
| :-- | :-------------------------------------------------------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------- | :---------------------------------------------- |
| T1  | Password guessing on login                                            | bcrypt cost 12, 5-failure lockout for 15 minutes, 10 attempts per minute per address, the same `401` for unknown email and wrong password.                                                 | A known email can be locked on purpose, and `423` shows the account exists.  | Implemented                                     |
| T2  | Stolen session                                                        | HttpOnly SameSite cookies, 15 minute access token, rotating hashed refresh token, tokens kept out of response bodies unless `X-Token-Mode: body`.                                          | An access token stays valid until it expires, up to 15 minutes after logout. | Implemented                                     |
| T3  | Cross-site request forgery                                            | SameSite `Lax` cookies, JSON-only bodies, no data change on GET, one origin.                                                                                                               | Low. Relies on browsers honouring SameSite.                                  | Implemented                                     |
| T4  | Replay of a refresh token                                             | Single use, rotation, only the SHA-256 hash stored.                                                                                                                                        | A reused token is refused but does not end the user's other sessions.        | Implemented                                     |
| T5  | Google sign-in attacks (forged state, open redirect, forged ID token) | Random single-use state for about 10 minutes, relative redirect paths only, ID token verified, PKCE supported, Google tokens never used as SwiftDrop tokens.                               | Trust in Google's verified email when matching an existing account by email. | Planned (M3.1)                                  |
| T6  | Account enumeration                                                   | Same `401` for unknown email and wrong password, same `202` for forgot password. Registration and lockout do reveal an account (`409`, `423`).                                             | Registration and lockout replies still show that an email exists.            | Partly implemented                              |
| T7  | Password reset abuse                                                  | 30 minute single-use hashed token, only the newest link works, link built from configured URL, rate limit per address and per email.                                                       | Anyone with mailbox access can reset the password.                           | Planned (M3.3)                                  |
| T8  | Forged or abusive webhooks (including server-side request forgery)    | HMAC SHA-256 over timestamp and body, 5 minute replay window, HTTPS-only targets that cannot be localhost or private addresses, 10 second timeout, 6 attempts.                             | A merchant that skips signature checks is unprotected on its side.           | Planned (M9)                                    |
| T9  | Event replay, duplicates and out-of-order events                      | Outbox in the same transaction, every consumer de-duplicates by event ID, merchant sync ignores events older than `last_status_at`, failures go to dead-letter queues.                     | A consumer that fails repeatedly parks the event for manual review.          | Partly implemented                              |
| T10 | Personal data exposure                                                | Addresses and phones excluded from events, logs, WebSocket messages and errors. Public tracking returns only status, cities and timeline. A redacting log handler masks sensitive fields.  | Developers must keep using the shared logger.                                | Implemented, tracking planned                   |
| T11 | Leaked secrets                                                        | Environment variables only, `.env` ignored by Git, placeholders in `.env.example`, no secrets in logs, passwords and tokens and API keys stored only as hashes, webhook secrets encrypted. | A secret pasted into chat or a ticket is outside the code's control.         | Implemented (webhook encryption planned)        |
| T12 | Access to another user's data, or a higher role                       | Role checks plus object-level checks in each service, `404` for records the caller does not own, role read from the signed token, role changes only by Admin.                              | A changed role takes effect only after the access token expires.             | Partly implemented                              |
| T13 | Forged service-to-service calls                                       | `/internal` is never routed by the gateway and needs `X-Internal-Token`.                                                                                                                   | Anyone on the internal network with the token.                               | Gateway block implemented, token planned (M3.4) |
| T14 | Malicious upload                                                      | JPEG or PNG only, 5 MiB limit, signature and full decode check, 16 megapixel limit, generated file name, never a public path.                                                              | An image that decodes but is unwanted content.                               | Validator implemented                           |
| T15 | Rate-limit bypass with a forged header                                | The limiter keys on the gateway's `X-Real-IP`, which Nginx overwrites, and ignores `X-Forwarded-For`.                                                                                      | Per-instance counters only.                                                  | Implemented                                     |
