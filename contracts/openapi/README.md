# OpenAPI contracts

One specification per HTTP service:

| Service  | Specification   | Public base path    |
| -------- | --------------- | ------------------- |
| Identity | `identity.yaml` | `/api/v1/identity`  |
| Parcel   | `parcel.yaml`   | `/api/v1/parcels`   |
| Pricing  | `pricing.yaml`  | `/api/v1/pricing`   |
| Merchant | `merchant.yaml` | `/api/v1/merchants` |
| Realtime | `realtime.yaml` | `/api/v1/realtime`  |

The public base paths are the Nginx routes. Nginx strips that prefix before forwarding, so service routers expose `/healthz` and `/readyz` at their root. See `docs/architecture.md`.

All specifications use OpenAPI 3.0.3 and are maintained by hand. When an endpoint is added or changed, update the specification, the Gin route, and the Nginx mapping together. No code-generation pipeline is used during initialization.

The current specifications intentionally describe only the operational health endpoints. Business endpoints will be added as they are implemented.

## Actual HTTP behavior

Every service shares the same router behavior:

- `GET /healthz` returns `200` with `{"status":"ok"}`.
- `GET /readyz` returns `200` with `{"status":"ready"}`. Readiness performs no PostgreSQL, RabbitMQ, or other dependency check yet, so it is not proof that downstream infrastructure is available.
- Responses are JSON and include an `X-Request-ID` header, either echoed from the request or generated by the service.
- Any unmatched path returns `404` with the standard error envelope and code `not_found`.
- A disallowed method on a known path returns `405` with the standard error envelope, code `method_not_allowed`, and an `Allow` header listing the permitted methods.
- An unexpected server error returns `500` with the standard error envelope and code `internal_error`. Internal details, stack traces, and credentials are not exposed.

The standard error envelope is:

```json
{ "error": { "code": "not_found", "message": "route not found" } }
```

The `404`, `405`, and `500` responses are documented on each operation because the handlers are shared by the whole service. Each specification defines `ErrorResponse`, `ErrorDetail`, `NotFound`, `MethodNotAllowed`, and `InternalServerError` components so future business endpoints can reuse the same shapes.

The current `code` values are `not_found`, `method_not_allowed`, and `internal_error`. New error codes must be added to the specification when the corresponding endpoint is implemented; do not invent business error codes in advance.
